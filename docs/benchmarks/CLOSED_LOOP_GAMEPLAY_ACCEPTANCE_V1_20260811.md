# 游戏闭环 Benchmark 与验收合同 V1

**状态：** 需求已确认，仿真实现和数值阈值尚未开始
**确认日期：** 2026-08-11
**上游产品合同：** [瞄准控制产品合同 V1](../project/AIM_CONTROL_PRODUCT_CONTRACT_V1_20260811.md)

## 1. 它要解决什么问题

旧 benchmark 主要评价内部误差、输出曲线或预设目标轨迹。它可以证明“命令看起来更平滑”，
却不能证明这些命令经过游戏以后真的让准星更好，也不知道用户当时是在修正、压枪、退出还是换人。

因此一个候选版本可能在内部成绩上提升 20%—30%，同时在真实游戏里：

- 把错误目标点当成正确答案；
- 顶住用户下拉；
- 在脱钩阈值处突然释放；
- 最终让视角甩到地面。

V1 benchmark 的责任是让这种版本自动判失败，而不是给它更高总分。

### 实施边界：V1 是终局合同，不是一次性开发清单

本文定义最终需要守住的产品结果，但不要求第一阶段就重建完整游戏、完整 Vision 数据集或
所有 COD profile。实施按证据逐层升级，后一层只有在前一层已能稳定区分好坏时才开始：

1. **Phase 0 — 单事故 RED 门槛：** 复用真实 `NativeGamepadController`，固定目标身份、
   错误纵向目标点、用户持续下拉、cue／释放时序和反事实输入；只判断“下拉是否得到及时
   响应”与“释放时是否出现输出阶跃”。当前已知坏版本必须以非零状态退出。
2. **Phase 1 — 微型闭环：** 在现有 Sustained AimLab 的响应曲线、延迟和目标运动模型上，
   加入已经通过 Phase 0 定义清楚的用户意图与硬门槛。总分只用于观察趋势，不能覆盖硬失败。
3. **Phase 2 — 实测校准：** 用同步的手柄输入、运行时遥测和画面运动标定 COD 共享 profile；
   没有实测证据的参数必须标为假设，不能以“拟真”名义决定发布。
4. **Phase 3 — 场景扩展：** 只有真实事故证明现有夹具缺少某类视觉或游戏机制时，才增加
   对应场景。默认不训练 Body／Pose 模型，也不为每个游戏复制一套模拟器。

因此，Phase 0 的目标不是证明整个游戏表现优秀，而是先证明测试工具能够抓住一个已经由
真人确认、旧 benchmark 却漏掉的坏行为。它是后续闭环投资是否值得继续的最低成本验证。

## 2. 什么叫闭环

最小闭环必须重复执行下面的因果过程：

```text
当前游戏画面 / 场景状态
  -> 真实生产 Vision、目标选择和控制链
  -> 最终手柄输出 T
  -> 已标定的游戏响应模型
  -> 下一帧准星、目标和画面状态
  -> 再送回同一条生产链
```

关键区别是：本帧的错误输出必须改变下一帧，错误能够积累、反弹和影响后续状态。
只读取一段固定视频并记录输出是开环诊断，不足以单独决定发布。

不需要制作完整游戏引擎。游戏响应模型只需忠实表达与瞄准相关的部分：

- 摇杆死区和响应曲线；
- FOV、ADS 和瞄具缩放；
- 游戏原生辅助瞄准／减速；
- 帧时间、输入到画面延迟和命令保持；
- 玩家与目标相对运动；
- 开火扰动和后坐力；
- 准星、人体区域和视角边界。

## 3. COD 产品族的仿真方式

最近几代 Call of Duty 使用相同或高度相近的引擎与输入体系，因此 benchmark 使用
一个共享闭环核心和一组可标定 profile，而不是每个游戏复制一套模拟器。

每个 profile 只描述实测差异：

- 游戏标题和版本；
- 帧率／帧时间；
- FOV、分辨率、ADS 和瞄具；
- 灵敏度、死区和响应曲线；
- 原生辅助瞄准的减速／吸附响应；
- cue 与敌我视觉配置；
- 武器或开火扰动配置。

共享引擎是减少适配成本的依据，但不能当成“曲线必然相同”的证据。
Black Ops 7 参考视频是首批事故证据；其他 COD 版本通过 profile 校准接入同一验收合同。

## 4. 每个场景必须有的“标准答案”

这里的标准答案只给评分器使用，生产算法不能读取它。可以把它理解成考试的答案纸。

每一帧或每个明确时间段至少记录：

| 真值 | 普通含义 | 为什么必须有 |
| --- | --- | --- |
| `I_truth` | 正确目标是谁 | 防止准星很稳但跟错人仍得高分 |
| `R_truth` | 当前允许的人体区域 | 不强迫所有姿态都瞄检测框中心 |
| `D_truth` | 用户此刻想瞄的位置 | 判断人工修正是否真的生效 |
| `intent_truth` | 微调、跟枪、压枪、退出或换人 | 同一个摇杆数值在不同场景含义不同 |
| `authority_truth_x/y` | 横轴和纵轴此刻应由谁主导 | 捕获“横向该跟、纵向该让”的案例 |
| `lifecycle_truth` | 获取、到位、跟随、cue、退出 | 判断状态进入和释放是否正确 |
| `forbidden_events` | 本场景绝不能发生什么 | 建立不允许被平均分抵消的硬失败 |
| `timing_windows` | 最晚何时必须响应 | 捕获拉不动、延迟释放和慢性残余 |
| `plant_profile` | 游戏怎样响应摇杆 | 让输出真正影响下一帧画面 |

没有这些真值，闭环只能知道“移动了多少”，不知道“移动得对不对”。

这不表示用户要逐帧填写整张答案纸。用户只需标出“想瞄谁、想往哪修、何时退出／换人、
什么结果绝不能发生”等产品事实；工具从同步视频、输入和遥测生成坐标与生命周期候选，
由工程侧复核。纯合成场景的逐帧真值由场景生成器直接产生。

## 5. 用户输入来源

一个场景可以组合三种输入来源，但必须标明来源和意图：

1. **语义脚本：** 精确生成微调、持续输入、甩枪、退出和换人，保证可重复；
2. **真人录制：** 保留真实力度、停顿和变向，用于校准脚本与用户模型；
3. **参数化用户模型：** 在已校准范围内批量扫不同反应速度和力度。

三者使用同一个生产链、同一个游戏响应接口和同一套评分规则。
参数化模型不能在没有真人录制校准时自称“真实用户”。

## 6. 安全条件不能变成延迟流水线

自动开火资格、目标可信度和 cue 禁火都是同一实时计划上的并行条件。
实现不得为每个条件增加独立等待窗口，也不得按顺序等待多轮确认。

初始合同是：

- 上游由连续新鲜观察稳定确认的身份可在当前帧复用，不再额外 dwell；
- 当前单帧首次检出不能直接开火，但这是身份链的既有确认责任，不是新增的开火等待队列；
- 当前帧同时检查 direct、hostile、inside-fire-region、not-cue 和 auto-fire-armed；
- 条件满足即可在当前控制决策中产生合成开火；
- 条件缺失只让该次合成开火为 false，不阻塞瞄准、物理开火或下一帧处理。

benchmark 必须单独记录“首次满足开火资格到合成开火输出”的延迟，防止安全实现演变成多级排队。

## 7. 硬失败门禁

以下事件默认零容忍。发生一次就判场景失败，不允许用平均误差或平滑分抵消：

1. 错误目标身份获得瞄准权限；
2. 没有用户换人意图时自动切换目标；
3. 用户进行合法人体内修正却被持续顶住；
4. 退出阈值前拉不动、越过阈值后突然释放或甩飞；
5. 友方获得瞄准或合成开火权限；
6. cue-only 状态合成开火；
7. 过期、跨目标代次或已失效目标继续拥有权限；
8. AI、Vision 或遥测故障导致原始手柄输入丢失；
9. 输出出现 NaN、越界、非预期尖峰、卡键或残余轴值；
10. 场景未触发目标路径却报告测试通过。

硬门禁可以在后续证据下细化，但不能为了让候选变绿而临时删除。

## 8. 需要连续评分的结果

通过硬门禁以后，才比较性能指标：

- 进入 `R` 的时间分布；
- 准星处于 `R` 的时间占比；
- 到 `D` 的屏幕误差 P50/P95；
- 目标变向后的跟随落后和恢复时间；
- manual 意图到正确屏幕响应的 P50/P95；
- AI 与合法 manual 方向冲突的持续时间和面积；
- 退出时间、释放输出阶跃和释放后过冲；
- 区域内振荡、方向反转和速度脉冲；
- cue 进入、维持、重见和到期释放时间；
- 合成开火正确率、漏触发和误触发；
- 采集到 Vision、Vision 到 controller、controller 到 ViGEm 的 P50/P95/P99；
- CPU、GPU、控制频率、Vision 频率和数据丢失。

产品层屏幕结果是主指标。内部输出曲线和阶段延迟用于解释问题，不能代替屏幕结果。

## 9. 首版场景集合

### P0：用户控制权和已知事故

- 同一人体内上下左右微调；
- 错误初始 `D` 下的人工纠正；
- 边界内持续输入到边界外退出；
- 换目标甩动；
- cue 纵向坐标偏差；
- 开火、人工下拉和 AI 压枪同时出现；
- cue 到期、目标死亡和 ADS 释放。

### P1：定位和跟随

- 静止目标获取；
- 横向、纵向和混合目标运动；
- 玩家自身横移；
- 双方同时运动；
- 快速变向、跳跃、滑铲；
- 站立、蹲伏、趴下和只露头。

### P2：身份和安全

- 多目标交错；
- 用户明确换人和无意图不换人；
- 友方进入当前目标区域；
- 新鲜无目标、过期数据、跨代次 cue；
- Vision、手柄、配置和遥测故障；
- 不同帧率、Vision cadence、丢帧和尾延迟。

场景优先级表示实现顺序，不表示 P1/P2 可以永久缺席最终 V1。

## 10. 参考视频事故的回归草案

### 10.0 2026-08-11 实施检查点

Phase 0 已按“事故形状回归”实现，benchmark runtime、闭环 plant 和评分器本轮未改动。专用 native
fixture 直接运行生产 `NativeGamepadController`，并固定同一目标、直接观察、cue、持续
向下输入和新鲜无目标释放。它不是参考视频的逐帧回放，也不能替代真实 COD 验收。

固定 known-bad 结果为：直接阶段向下响应增量 `0.546220`、cue 阶段 `0.142001`、
权限释放阶跃 `0.734222`，因此 O2/O3 为 RED。保持相同阈值运行重构候选后，结果为
`1.116667`、`0.876222` 和 `0.000000`，三个 oracle 全部 GREEN。

该结果只证明：新的 owner 合同能够抓住并消除夹具中的“输入被顶住／释放悬崖”。
它尚未证明轻量 `R` 在视频里的机瞄遮挡、人体姿态和游戏响应上准确，也没有授权用这组
内部 normalized-stick 数值替代 Phase 1 的屏幕闭环与 matched live session。

全量测试曾暴露一个旧 oracle：慢／带噪 manual 虽减少错误锁定帧，仍发生错误目标强吸附，
旧断言却要求总分提高。按照本合同“错误身份一次即失败”，该测试已改为保持 0 分硬失败；
没有因此修改 benchmark 场景、plant、评分公式或生产参数。

**事故 ID：** `wrong-d-manual-down-threshold-detach-20260811`
**状态：** `draft`，不是 RED 证明
**建议表面：** 带游戏响应模型的 native replay／闭环 benchmark

### 10.1 已确认事实

- `F1`：AI 初始定位相对实际期望位置偏左上。
- `F2`：用户尝试向下修正，同时存在压枪意图，但屏幕没有按预期向下响应。
- `F3`：manual 达到退出阈值后，AI 突然释放，视角快速落向地面。
- `F4`：现象可在用户提供的 Black Ops 7 视频约 7 秒开始观察。

### 10.2 目前只能作为推断的内容

- `I1`：错误 `D` 可能来自机瞄／cue 高度或坐标重建；视频症状不能单独证明具体代码 owner。
- `I2`：拉不动后突然甩飞与阈值两侧权限不连续相符；仍需同步输出和状态证据定位具体 tick。
- `I3`：人工下拉可能同时包含目标内纠正和人工压枪，不能只按幅度归为一种意图。

### 10.3 未知信息

- 事故对应的准确 executable SHA-256 和 source commit；
- 同步的物理右摇杆、开火、LT、目标代次和 cue 状态；
- 当时游戏 profile、武器／瞄具、FOV、帧率和遥测模式；
- AI 反向输出、释放输出阶跃和屏幕运动的逐帧数值。

在这些身份补齐前，任何合成 fixture 只能是事故形状的近似，不得声称已经建立 known-bad RED。

### 10.4 必须证明触发过的路径

未来 fixture 必须断言：

1. 一个目标身份已经获得 ADS／跟随权限；
2. 当前 `D` 位于正确人体区域的左上方或上方；
3. 用户产生持续向下 manual；
4. firing/recoil 状态按事故证据明确启用或关闭；
5. AI 在纵轴仍有实质权限；
6. 输入最终跨过退出边界并触发释放。

如果目标从未被接纳、manual 没有到达、AI 纵轴本来就空闲或退出没有发生，测试不得通过或失败后冒充本事故。

### 10.5 事故症状 oracle

数值阈值在 known-bad 录制和真实 profile 标定后冻结，但 oracle 方向现在固定：

- `O1 manual_ack`：向下修正后，屏幕纵向必须在允许窗口内开始向正确方向变化；
- `O2 opposition`：AI 不得在错误 `D` 上持续产生抵消合法下拉的纵轴面积；
- `O3 desired_update`：人体区域内下拉必须更新 `D` 或释放纵轴权限；
- `O4 release_continuity`：退出前后最终 `T_y` 不得出现超限阶跃；
- `O5 detach_overshoot`：释放后的向下屏幕过冲不得超过用户意图和游戏响应允许范围；
- `O6 identity`：整个主要场景保持同一 `I`，除非 counterfactual 明确引入换人；
- `O7 fire_source`：cue-only 或敌方证据不足时不得合成开火。

### 10.6 反事实控制

- `C1`：把初始 `D` 放回正确上胸区域，应消除“纠正错误 D”的触发，但不能破坏普通压枪；
- `C2`：移除 manual 下拉，`manual_ack` 不适用且不得伪造人工抑制失败；
- `C3`：保留 manual 但不越过退出边界，不应发生脱钩释放；
- `C4`：使用直接人体证据代替 cue，应验证人工修正规则仍一致；
- `C5`：加入第二可信目标和明确甩动，才允许身份切换路径执行。

### 10.7 建立 RED 前的阻塞项

该草案还缺 known-bad runtime 身份和同步输入／状态证据。因此当前工作只能冻结产品症状、
fixture 协变量、触发条件和 oracle，不能填写假的失败数值或 runtime hash。

下一步若选择把该视频正式变成 RED，先定位同次 session 的 manifest、telemetry、配置和 executable hash；
若不存在同步证据，则用同一游戏 profile 复现并录制一次新的 matched known-bad 事故。

## 11. 防止“测试自己骗自己”

每个正式 fixture 必须具有：

1. 至少一个触发断言，证明目标路径真实执行；
2. 至少一个与外部症状对应的量化 oracle；
3. 至少一个改变触发后会改变结果的反事实；
4. 所有相关轴、生命周期、manual、left-stick、firing、freshness 和 cadence 协变量；
5. 含实际测量值的报告，不接受只有 `passed=true`；
6. known-bad 和 candidate 两个不同、完整的 runtime SHA-256；
7. 不变的 fixture 和 oracle，不能看完候选结果再改门槛。

局部单元测试和开环回放可以用于定位，但不能单独把候选版本提升为产品基线。

## 12. 每次比较必须绑定的身份

任何可比较结果至少记录：

- source commit 和工作区是否干净；
- executable SHA-256；
- 完整运行配置及哈希；
- Vision 模型／TensorRT engine 及哈希；
- 场景集、fixture schema、seed 和报告 schema；
- 游戏标题、版本和 plant profile 哈希；
- FOV、分辨率、帧率、灵敏度、死区、瞄具和武器；
- CPU、GPU、手柄、驱动和显示刷新率；
- telemetry／performance logging 模式；
- 同步视频、输入 trace 和结构化遥测的 artifact ID／哈希。

缺少关键身份的结果只能作为历史线索，不能与当前基线做百分比结论。

## 13. 发布顺序

候选版本只有按以下顺序通过才可替换基线：

1. 已知事故和全部硬失败门禁；
2. COD profile 下的闭环仿真；
3. 真实 ViGEm／采集／调度链路回放；
4. 固定真实游戏场景；
5. 一段自由实战和用户手感确认。

“自动 benchmark 全绿”不等于“产品已通过”。真实游戏失败必须回到固定事故 fixture，
不能只靠下一次自由体验声称修复。

## 14. 实现前门禁

本文件没有批准 benchmark 实现。开始写代码前必须先完成：

1. review 当前 benchmark、replay、telemetry 和 production adapter，确定可以复用的唯一入口；
2. 冻结 fixture schema、游戏响应接口和报告 schema；
3. 从一段 matched COD 录制标定第一个 plant profile；
