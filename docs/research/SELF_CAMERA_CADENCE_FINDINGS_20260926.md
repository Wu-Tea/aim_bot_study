# 自身视角变化：高频算法检查

本次检查沿“玩家推动视角时算法跟不上”的方向展开，发现两个可以直接复现的算法问题。没有新增动作识别规则，也没有修改生产控制行为。它们是代码和局部执行支持的问题，不是已经确认的全部实战过冲根因。

第一个问题是**视觉更快后，估计器可能完全停止接收样本**。通用与 ADS 响应学习要求相邻观测间隔至少 5 ms，BodyLock 运动估计要求至少 4 ms。NativeGamepadController 每来一帧都会更新用于计算下一对差分的时间与位置，即使这次观测被估计器拒绝。因此短间隔不会累计为有效区间。大于 200 Hz 的稳定视觉流不能进入这两个响应学习器；大于 250 Hz 的稳定视觉流连运动估计也不能建立。

探针使用实际 NativeGamepadController 和 OutputComposer，目标身份固定。视觉位置按明确的已发送镜头指令生成，目标在世界中静止。学习回执来自脚本指定的输出，目的是单独检查自身镜头运动是否被正确识别，不把控制器提案接入游戏反馈环。没有左摇杆动作、跳蹲、开火、压枪、检测噪声、辅瞄或传输延迟。控制器响应设为 500，合成镜头响应也为 500。X/Y 分别运行一秒，0.25 秒后统计有效运动估计；每组都持续处于 BodyLock，避免“没有进入路径”的空通过。

响应学习另用实际 AimResponseEstimator 和 AdsResponseEstimator 做隔离测试，输入正负 0.1 的明确激励、800 的已知响应及完全可信的观测。下面样本数属于这两个组件测试，不表示控制器回放中的在线学习数；后者为隔离运动估计而关闭了学习。

| 新鲜视觉频率 | BodyLock 有效运动帧 / 已进入帧（每轴） | 通用响应接受样本 | ADS 响应接受样本 |
|---:|---:|---:|---:|
| 100 Hz | 74 / 74 | 99 | 95 |
| 160 Hz | 119 / 119 | 159 | 155 |
| 200 Hz | 149 / 149 | 199 | 195 |
| 250 Hz | 187 / 187 | 0 | 0 |
| 320 Hz | 0 / 239 | 0 | 0 |
| 500 Hz | 0 / 374 | 0 | 0 |
| 1000 Hz | 0 / 749 | 0 | 0 |

160 Hz 下没有触发这个拒收问题，因此不能用它直接解释用户在 160 Hz 下的全部症状。这里讨论的是**新鲜视觉观测频率**，不是循环重复使用旧画面的频率。间隔抖动时可能间歇接受，而非上述稳定节奏下的完全拒绝。

第二个问题是**AI 输出整形人为延迟换向，而且延迟随控制频率变化**。AimDynamicsShaper 使用每秒变化率和每 tick 最大变化量 0.08 的较小值；反向时先把旧方向降为零。探针先把同一目标的状态设为 +0.8，再持续请求 -0.8，保持身份、生命周期与模式不变。抵达零所需时间如下，还不包括向负方向建立输出的时间：

| 控制更新频率 | 旧方向从 +0.8 收到零 |
|---:|---:|
| 160 Hz | 62.5 ms |
| 250 Hz | 40 ms |
| 320 Hz | 31.25 ms |
| 500 Hz | 20 ms |
| 1000 Hz | 17 ms |

这些是组件执行结果，不能直接称为游戏实测延迟。尤其不能把 Vision 为 160 Hz 自动等同于 shaper 也是 160 Hz。最终人工仲裁位于 shaper 后面，这些时间描述 AI 提案路径，不表示原生摇杆透传被加了相同延迟。

动作处理方面，现有 controller 已使用左摇杆 X 作为横移证据，并在短暂失去人物、开火扰动等条件下使用受限历史快照。TargetCoordinator 中的 Jump/Fall 标签由画面速度生成，不能证明玩家按下了跳跃或蹲键；检索没有发现这些标签直接参与本次检查的运动估计或输出整形。物理按键本身已有输入与 DS4 映射，但游戏动作语义取决于玩家的按键绑定。

后续修复应先让观测区间的管理兼容高频输入，并保证失败、换目标、开火歧义等状态不会被累计跨越；然后把换向制动的要求按实际时间表达，检验是否还需要“先退零”的两阶段限制。不能直接缩短全部阈值或删除全部滤波：此前消融已经出现过索敌、跟踪退化。左摇杆和动作输入保留为上下文证据，当前已有两个不依赖复杂动作的明确检查点。
