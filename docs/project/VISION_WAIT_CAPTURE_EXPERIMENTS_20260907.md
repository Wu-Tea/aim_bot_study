## 需要解决的原始症状

最新实际运行会话为 `20260907T091913Z_100820_1`。开镜有效视觉更新约 164.91 Hz；首次开镜窗口后的混合阶段，CPU output_wait 平均 2.955 ms、GPU event span 1.686 ms，逐帧截零残差均值 1.293 ms。有目标第 8568 帧的捕获复制段为 12.391 ms，结果交付另有 5.500 ms。

这些字段不能证明操作系统唤醒、GPU 排队、驱动或 D3D 复制中的某一个是根因。尤其 `capture_copy_complete_ns` 是 Copy/Flush/ReleaseFrame 后的 CPU 时间戳，不是 GPU copy fence。完整日志审计在 `artifacts/telemetry-audits/20260907-latest-performance/REPORT.md`。

## 本轮方法与限制

- 同进程 ABBA；每个对照只改变等待方式或桌面帧持有方式。
- 同一原始 TensorRT engine、160 张固定训练裁剪、640×512 BGRA → 480×384 tensor、阈值 0.20。
- 同步实验：每阶段 32 秒，前 8 秒不参与稳态统计，最后 1 秒排除；GPU 每 500 ms 采样。基线和候选各两个阶段。
- 22 Hz 初测在基线出现 17.916% GPU 占用；16 Hz 复测在第二个候选阶段出现 15.045%，均停止且不算合格结果。保留失败记录，没有放宽 15% 上限。
- 完成的同步对照使用请求 10 Hz，实际约 9–10 Hz。这是等待机制实验，不是当前游戏帧率、极限吞吐或 15% 预算下的游戏能力测量。
- GPU 预算指该进程 Windows PDH 最忙 GPU engine 的稳态采样最大值，不代表瞬时硬上限或整卡占用。初始化不计入该判据。
- GPU 时钟随阶段明显变化，不能拿总耗时均值直接认定候选的纯因果收益。额外报告同帧 `wall_ms - gpu_total_ms`，它仍是诊断差值，并非精确的线程唤醒时间。
- `GetThreadTimes` 在这些样本中呈现 15.625 ms 量化，CPU 时间仅以大量样本的累计值/平均值解释，不解释逐帧 CPU P95/P99，也不外推 165 Hz 下的资源占比。
- 本轮未检测到游戏进程，缺少匹配的实际游戏 Present/帧时间，因此不能声称改善或保护了游戏吞吐。

把推理输出复制后的 `cudaStreamSynchronize` 替换为 `cudaEventSynchronize`，完成事件带 `cudaEventBlockingSync`。GPU 命令、地址、Graph 和检测结果不变。

| 项目 | 基线两阶段 | 候选两阶段 |

| wall − GPU span 均值 | 0.128 / 0.137 ms | 0.626 / 0.666 ms |
| wall − GPU span P99 | 0.331 / 0.490 ms | 10.112 / 9.729 ms |

四阶段 160 个输入全部覆盖，260 条检测/空图记录逐项完全相同。

**拒绝进入主线。** 明确减少了等待期 CPU 消耗，但引入的长尾不满足本项目实时性要求。这没有证明原日志的 1.293 ms 都来自忙等，也没有解决 GPU 排队。

## 实验二：持有 DXGI 桌面帧到下一次抓取

捕获对象持有 frame lease；下一次 AcquireNextFrame 前释放；显式停止、重建、异常与析构负责清理。记录整个 grab 调用，包括前一帧的 ReleaseFrame，避免把成本挪到统计边界外。另拆分 CopySubresourceRegion、Flush、ReleaseFrame 的 CPU 耗时。

实际桌面访问最初被沙箱拒绝，DuplicateOutput 返回 0x80070005；经所需桌面访问权限运行后完成验证。图像只在内存中比较，没有保存桌面图像，也没有发送手柄输入。

- 85 个有效样本验证复制后的 ROI 在下一次 grab 前保持逐字节稳定。
- 覆盖立即释放/延后释放切换、重复显式释放、重建后 lease 清空。
- 未覆盖真实显示模式切换、设备丢失、所有异常注入，也未把这些检查称作完整生命周期回归。
- 30 Hz 请求、4×16 秒桌面对照；稳定阶段实际新帧约 21 Hz，不能替代 165 Hz 游戏场景。

| 项目 | 立即释放两阶段 | 延后释放两阶段 |
|---|---:|---:|
| grab 均值 | 0.318 / 0.331 ms | 2.808 / 2.920 ms |
| grab P99 | 0.988 / 0.977 ms | 10.533 / 13.754 ms |
| GPU 采样均值 | 0.236 / 0.259% | 0.211 / 0.258% |

**拒绝进入主线。** 没有稳定的 GPU 收益，取帧延迟明显增加。微软的资源节省建议不等价于本项目的低延迟最优解；这也不能证明原来 12 ms 停顿由 ReleaseFrame 单独导致。

## 实验三：高精度计时器检查完成事件

每次查询真实 CUDA 完成事件；尚未完成时，用 Windows 高精度 waitable timer 等待 100 微秒再查询。无渲染预测、无动态 capture_fps、无优先级提升、无虚假完成；CUDA 错误继续传播，计时器创建或等待失败直接报告失败。

同样完成 ABBA，四阶段的 160 个输入/260 条记录全部完全一致；每阶段 GPU 采样最大值均低于 15%。CPU 消耗显著降低，但第一个候选阶段 `wall − GPU span` P99 达 9.706 ms，而其前面的基线为 0.278 ms。具体四阶段值见 `artifacts/vision-sync-wait-20260907/timer10/wait-residual.json`。

**不进入主线。** 100 微秒计时器请求并不保证线程在 100 微秒后获得调度；本轮不能保证长尾不回退，不能只展示省 CPU 的一面。

## 当前结论与继续工作的必要条件

目前没有能同时降低 CPU/GPU 等待、避免长尾回退且证明不损害游戏吞吐的候选。继续保留当前生产实现，不把以上探索称作修复或发布优化。

下一步需要游戏运行在可重复场景，再同步观测：

1. GPU 工作的提交与实际执行间隙，以及 CUDA 同步返回前后的 CPU 调度；
2. Capture 的 Copy、Flush、ReleaseFrame、Acquire 分段；
3. 结果发布、Controller 消费、ViGEm 更新分段；
4. 游戏自身 Present/帧时间与进程 GPU 占用。

应先对自然基线抓到原始长尾，再在确证的所有权层修改。不能用人为 sleep 模拟 GPU 排队来宣布 RED→GREEN，也不能用空载探针替代游戏吞吐验收。用户不需要另录视频；缺的是实际游戏负载和调度证据。

### 推理等待：新增的直接证据

下表两列是不同时间的诊断样本，**不是基线/候选，也不代表优化收益**。数值均为毫秒均值。

| 时段 | 轨迹一，45 帧 | 轨迹二，44 帧 |
|---|---:|---:|
| 输入复制 API 返回 → GPU 开始复制 | 1.276 | 0.241 |
| CPU 进入 StreamSynchronize → GPU 开始输入复制（有符号） | 0.967 | -0.200 |
| 输入复制实际设备活动 | 0.0114 | 0.0116 |
| 预处理 kernel 实际设备活动 | 0.0088 | 0.0091 |
| TRT Graph 设备首尾跨度 | 3.862 | 2.183 |
| Graph 内 kernel 间隙合计 | 0.224 | 0.069 |
| 输出 D2H 完成 → StreamSynchronize 返回 | 0.0222 | 0.0424 |

轨迹一中，CPU 已进入同步调用，GPU 仍平均过 0.967 ms 才开始输入复制。这段时间不能解释为“GPU 已完成但 CPU 没醒”。GPU 输出复制完成后的 CPU 返回 P99 为 0.054 ms；轨迹二有一个较大的返回延迟，最大 0.807 ms，因此也不能宣称 CPU 返回永远没有长尾。

这缩小了本次慢样本的调查范围：输入提交后的启动间隙比输入复制与预处理本身大得多。不能从 CUDA 时间线继续推定间隙一定由游戏抢占、WDDM 软件批处理、某个驱动或 CPU 调度单独造成；仍缺 OS 级调度轨迹。两段间隙差异大，且 node tracing、低采样率、时钟状态均影响结果。它与原日志约 1.293 ms 的诊断残差数值相近也不是同源证明。

**决策：** 停止把阻塞事件、计时器等待或重写缩放 kernel 当作当前主要修复方向。输入复制和预处理合计约 0.020–0.021 ms，即使消除这些设备活动，单凭这部分也没有毫秒级直接收益。下一种候选必须针对已证实的提交/执行间隙，并以完整延迟和游戏帧时间共同判定；不依据老版本驱动的非契约 flush 技巧直接改主线。

### 捕获长尾：尚未复现

NVTX 把原 `capture_copy_ms` 对应的 CPU 段拆成 CopySubresourceRegion、Flush、ReleaseFrame。在两段轨迹中，Copy 提交最大分别为 0.007 / 0.008 ms，Flush 最大 0.132 / 0.214 ms，ReleaseFrame 最大 0.078 / 0.165 ms。没有抓到原先 12.391 ms 的复制段停顿，因此不能决定应改 Copy、Flush、ReleaseFrame 哪一层。

这些 CPU 分段没有测量 D3D 复制的 GPU fence 完成时间；不能把 Copy API 很快等同于 GPU 复制已经完成。当前保留立即释放实现；上一轮延后释放候选的明显长尾回退仍然有效。

### 尚缺的关键证据

独立 PresentMon 1.8 会话启动失败，返回 ETW 错误 1450（系统资源不足）；当前 token 非管理员。另一版本未产生有效 CSV。只读会话清单显示现有多个系统/工具会话及 FrameViewService，但未查明资源不足的具体限制；不能直接归因于权限或会话数量。没有停止现有 FrameView、游戏、系统跟踪会话，也没有修改系统限制。
