# 手柄助手：重新建立配置工作区

用户打开应用，是为了选择一份配置、查看参数、作出少量调整，然后使用它。界面首先要把正在编辑的对象和当前数值说清楚。现有界面把同一个对象重复显示成顶部配置和页内场景，又用大标题、说明、标签、来源文字、控件分多行呈现每个参数，结果是页面占了很多空间，但用户看到的值很少。

本方案已经落地为 Tk 桌面配置工作室。配置管理、参数编辑、手动曲线、运行操作、学习反馈和原生内存帧率可实际使用；自动曲线识别与反曲线校准留作后续工作。原浏览器视觉稿仍使用演示数据，只用于设计对照；实际使用与存储格式见[配置工作室说明](DESKTOP_ASSISTANT.md)。

## 哪些方法适合这个工具

主机与电视先帮助用户在内容中选定对象，再用局部菜单完成常用操作。PS5 的控制中心保留当前游戏背景；BRAVIA 的快捷设置保留观看内容，完整设置放在更深一层。这种“当前对象不丢失”的组织方式值得采用，但远距离观看需要的大块空间不适合桌面参数工具。[PS5 官方说明](https://www.playstation.com/en-ca/support/games/customize-ps5-control-center/) · [BRAVIA 官方说明](https://helpguide.sony.net/tv/musltn1/v1/en-003/contents/TP1001675617.html)

索尼的创作工具更接近本应用。Imaging Edge 将预览、参数面板、对象切换和状态分开；曝光面板同时提供滑杆与数值；Catalyst 把预览、测量和参数放在一个工作区，次要操作在窗口变窄时收进菜单。由此推导出的本应用方案是：参数页用紧凑对齐行，曲线页把画布和坐标放在一起，文件操作不常驻成一排等重按钮。[Imaging Edge 工作区](https://support.d-imaging.sony.co.jp/app/imagingedge/en/instruction/3_1_retouch_display.php) · [参数面板](https://support.d-imaging.sony.co.jp/app/imagingedge/en/instruction/3_3_retouching.php) · [Catalyst 工作区](https://helpguide.sony.net/di-app/cp/v1/en/Content/Color_correction_editing.htm)

Apple 的参数工具提供了另一组依据。Photos 将整体调整与详细选项分开，Logic Pro 的检查器依附选中的对象，Motion 把参数值与曲线放在相邻区域。它们允许用户先完成当前调整，再进入细节。本应用因此把高级设置按功能组展开，并让参数说明和重置只在对应项附近出现。不能用一个“详细参数”总开关同时隐藏所有页面的主要内容。[Photos 调整面板](https://support.apple.com/en-asia/guide/photos/pht806aea6a6/mac) · [Logic Pro 检查器](https://support.apple.com/en-ae/guide/logicpro/lgcpe9cc3b1d/mac) · [Motion 参数与曲线](https://support.apple.com/en-mide/guide/motion/motn147486cf/mac)

配置选择和配置生效也必须分开。Compressor 的准备、进行中和已完成状态具有不同操作权限；Imaging Edge 的版本选择与设为当前版本是两个动作。这提醒我们：用户切换编辑的 Profile 后，运行状态仍必须指向真实运行的那份配置。顶部选择不能悄悄表示程序已经切换。[Compressor 状态与检查器](https://support.apple.com/guide/compressor/compressor-interface-cpsr8747af64/mac) · [Imaging Edge 版本管理](https://support.d-imaging.sony.co.jp/app/imagingedge/en/instruction/3_3_retouching.php)

## 从对象到动作

注意力按“选中的 Profile → 当前工作区的值 → 修改反馈 → 保存或启动”经过页面。当前 Profile 使用浅蓝选择面；参数使用稳定对齐；唯一高对比主按钮固定在右上方；保存反馈占用一条状态区。界面不再重复展示大号配置标题和同义说明。

打开应用先进入参数调校，因为这里是用户反复操作的主要工作。游戏场景是 Profile 身份的一部分，只在新建时选择。用户切换 Profile 时，参数、曲线和草稿一起切换。运行状态独立保留，明确显示真正运行的配置。新建、复制、重命名都围绕 Profile；参数的局部操作围绕参数，二者使用不同菜单。

## 如何提高密度并保持清楚

提高密度靠减少重复表达和稳定布局：标签与值同行，连续参数用滑杆加精确数值，开关不再附加一个“启用”标签，范围与说明按需查看。两列分别组织完整功能组，阅读顺序先列内、再另一列，避免把一个功能组拆到多个位置。数值右对齐并带必要单位，文件路径用文件名摘要，完整路径在编辑器中显示。

“降低信息熵”在这里落实为减少不必要的选择、重复控制和同义文字，不报告未经用户研究的熵值。增加字段数量时，要同时保持可读标签、可区分的控件、稳定的焦点顺序和足够点击面积。参数搜索用用户熟悉的名称和说明匹配，也会显示匹配的高级项；它不替代功能分组。

## 统一的视觉语言

视觉基调是深灰工作区、细分隔、浅蓝焦点。背景提供稳定对比，选中 Profile 和键盘焦点使用同一强调色。编辑控件有略亮的底色，状态与说明低于参数值的视觉权重。布局以功能组和对齐行建立结构，卡片只用于可选择的对象。

| 项目 | 规格 | 作用 |
| --- | --- | --- |
| 工作区 / 浮层 | `#171a20` / `#20242b` | 内容与菜单层级 |
| 输入 / 选择面 | `#292e37` / `#293c59` | 编辑区域与当前对象 |
| 主文字 / 次文字 | `#eef0f4` / `#9ca5b4` | 数值与辅助信息 |
| 焦点 / 分隔 | `#89baff` / `#343a45` | 明确选择与安静边界 |
| 输入错误 | `#f49090`，同时附文字 | 避免只靠颜色说明问题 |
| 字体 | Microsoft YaHei UI、Segoe UI；数值右对齐 | 单一字体体系与稳定数值列 |
| 字级 | 页面 18、分组 14、参数 12～13 px | 让标题留出内容空间 |
| 间距 | 4 / 8 / 12 / 16 / 24 px | 参数项与功能组有不同边界 |
| 参数行 / 菜单项 | 约 38 px / 至少 32 px | 密度与点击面积兼顾 |
| 边界 | 输入与选择面使用细边框，滑杆与开关用圆形手柄 | Tk 实现保持一致的控件识别 |

窗口默认采用桌面工具的紧凑比例。900×740 是首要设计尺寸，1120×840 用于检查宽窗口，840×680 用于最小窗口。宽窗口增加控件可用空间，不增加标题大小。常用参数维持两列；曲线高度随窗口收缩，坐标与主操作保持可访问。

## 控件必须表达怎样的操作

| 控件 | 默认与悬停 | 键盘或明确编辑 | 错误、取消与禁用 |
| --- | --- | --- | --- |
| 数值 | 当前值与单位同行；悬停不抢焦点 | 点击输入；Tab 定位；滑杆与数值同步 | 原样保留非法输入并就地说明范围；禁止提交 |
| 开关 | 显示当前开关态，名称不重复 | 点击或 Space 切换 | 忙碌时禁用，不把状态伪装成候选项 |
| 单选菜单 | 按钮显示当前值；菜单用勾标记已选值 | 上下键移动候选；点击或 Enter 提交 | Escape、Tab 或点击外侧关闭；未确认不改值 |
| 参数更多 | 不占用每行固定按钮位置 | 右键或 Shift+F10 查看范围、恢复创建时的值 | 恢复后成为草稿，保存前可继续调整 |
| Profile | 选中态和修改标记分开 | 点击或键盘选择；切换保留独立草稿 | 名称为空时就地提示；名称有效后才创建配置 |
| 曲线点 | 当前点突出，显示输入与响应坐标 | 拖动、坐标输入、方向键微调 | 端点固定，邻点不能交叉；非法坐标就地说明 |
| 主操作 | 根据状态显示启动、保存并启动或重启 | 明确点击才运行 | 保存或启动中禁用相关编辑；失败显示可执行的下一步 |

关闭的下拉、滑杆和数值框上，滚轮归页面所有。打开菜单后的滚轮也不提交候选值。仅鼠标进入不调用 focus，也不修改变量。Tab 和明确点击取得编辑焦点；为了露出键盘焦点而滚动是另一件事，不能由鼠标悬停触发。

单选菜单遵循互斥选项的语义，动作菜单则承载命令。曲线、配置和参数各自的动作菜单只提供相关操作。原生实现必须让菜单在窗口边界附近调整展开方向，关闭后返回打开它的控件，并在销毁页面时清理绑定。[Apple 单选菜单](https://developer.apple.com/design/human-interface-guidelines/pop-up-buttons) · [Apple 菜单规范](https://developer.apple.com/design/human-interface-guidelines/menus)

## 曲线的图形与精确编辑

曲线图保留输入与响应坐标、线性参考、当前控制点和保存基准。类型选择与曲线处于同一工作区；拖动内置曲线后成为自定义曲线，撤销时恢复原类型。导入、导出、保存预设位于局部工具栏，配置保存仍使用窗口顶部的统一操作。

图形拖动适合观察形状，坐标输入适合精确调节，二者共享同一组点。视觉稿采用现有原生 COD LUT 的真实采样点，不用任意形状冒充该模板。手柄曲线的端点固定为 `[0,0]` 与 `[1,1]`，输入和响应都严格递增，最多 32 点；它不能直接沿用图像调色曲线的全部自由度。[Final Cut Pro 的曲线编辑](https://support.apple.com/en-ca/guide/final-cut-pro/verf87ca7b62/mac) · [Motion 的图形与数值编辑](https://support.apple.com/guide/motion/modify-keyframes-in-the-keyframe-editor-motn147476b0/6.4/mac/26.6)

曲线持久化沿用版本化 JSON：`schema_version: 1`、`kind: normalized_stick_response`、`interpolation: piecewise_linear`、名称与归一化点数组。Profile 保存其曲线快照；曲线预设用于复制和复用，修改某份配置不能悄悄改动其他配置的曲线。保存状态与运行生效状态分别反馈，当前原生边界仍要求曲线修改后重启。

### 点位精校

拖动用来调整形状，精校用来确认某个点的准确坐标。点击图中的点，或在全部点位表中选择它，输入与响应坐标就显示同一个点。坐标以百分比表示，精校框显示最多六位小数；键盘上下键每次调整响应 0.1 个百分点，按住 Shift 调整 1 个百分点。双击控制点进入精校，全部控制点可以在图下展开成紧凑表格。

图形、当前点编辑器和点位表共用一份数组。非法坐标留在对应编辑器中并显示错误，不写入曲线；拖动受到邻点约束，端点固定，任何路径都不能绕过单调性限制。精校与拖动都属于当前 Profile 的草稿，保存前不会改动其他配置。

### 后续方案：从画面校准游戏死区与曲线

本节保留校准设计供后续实现讨论；当前桌面 GUI 没有自动识别、反曲线或视觉校准入口。下文描述目标与测量方案，不能作为功能已经实现的说明。“参数调校”中的手动输出补偿只编辑已有原生参数，通过箭头展开，不用开关表示次级设置入口。

这个功能的目的，是在游戏保留原有死区和响应曲线时，把送给游戏的摇杆输出转换成更接近零起动死区、线性的有效响应。它是按游戏和模式校准的输出适配器，与曲线编辑器保存的辅助意图曲线分别持有数据。校准测得的游戏响应不能覆盖用户设定的辅助曲线；手动输入由输出适配器线性化，AI 仍按用户设定的曲线工作。开启补偿会重映射最终摇杆输出，包括用户手动输入的贡献，因此默认关闭，明确启用后才生效。关闭时保持原有直接输出，原始输入记录与 AI 手动意图权重不改写。参数页不再重复放置另一组手动死区开关，补偿的启用与校准归这个工作区所有。

设已测得的游戏响应为 `r = F(u)`，用户希望的归一化响应为 `t`，适配器求输出 `u = F⁻¹(t)`。最终拟合依据实际测得的点，不预设游戏只有死区和幂指数。正输入越过游戏死区会产生输出跳变，这正是反死区的作用，不能用从 `[0,0]` 开始的普通线性插值悄悄抹掉这个语义。校准需要独立的格式与零输入规则，不能冒充一份 AI 手感曲线。现有视觉稿中的死区加幂指数仅为旧版理想模型示意，不能视作已确定的测量方法。

水平响应改用不同力度下的完整旋转周期作为主要测量。此处按用户的“360°”指固定输出力度，让游戏镜头水平转满一圈理解；摇杆方向绕圆的测量用于另行检查方向耦合，二者不能混为同一实验。

推荐实施候选是“整圈定标、局部加密、独立整圈复测”。不同方法按如下职责配合；该取舍依据角度尺度和低速采样耗时，尚未通过具体游戏实测证明耗时或精度优于逐档整圈测量。

| 方法 | 提供的证据 | 使用边界 |
| --- | --- | --- |
| 代表性力度的多圈计时 | 有明确 360° 尺度的平均角速度、逐圈稳定性 | 作为响应标定基准，正反向及不同模式分别测量 |
| 小力度与转折处的局部视觉 | 更密集的运动响应样本、起动与时间变化 | 先用可信整圈基准校验角度映射；没有可靠标定时只报告相对运动，不能标成 °/s |
| 留出力度的整圈复测 | 拟合预测与实际完整周期是否一致 | 不复用参与拟合的相同样本；失败时舍弃有问题的局部估计，追加整圈采样 |

局部视觉不得用全画面的像素平移除以时间来代替角速度。需要考虑透视、所处朝向、选取区域与 FOV；可在相同背景与朝向下建立和验证局部运动到转角的关系，或使用已标定相机模型估计旋转。没有可信映射时，保留整圈测量结果，将对应低力度范围标为未完成，而不是填入推测值。独立复测还要检查补偿后多个期望力度的角速度是否按比例变化，仅原始曲线拟合通过不足以证明线性手感。

应用发送一个固定水平输出力度 `u`，维持模式与游戏设置，视觉识别背景地标离开后绕行并再次经过同一朝向。相邻的可靠回归事件间隔为 `T` 时，整圈平均角速度是 `360° / T`；跨 `n` 个完整周期则为 `360° × n / Δt`。原始点记录力度、方向、模式、周期、角速度、重复次数和测量不确定性。整圈角度提供真实的尺度依据，不需要把局部像素速度直接当作转动角速度。

先做粗粒度力度扫描，再在起动区域、曲率变化处和高端饱和区加密。使用实际设备能表示且最终送达的输出档位，不用浮点精校位数冒充硬件分辨率。每个档位重复完整周期，并比较正反方向及上扫、回扫。用同一条件下可靠的最大稳定角速度归一化，得到响应点集，再拟合单调曲线；饱和平台保留其边界，多值区间不被强行拟合成可逆函数。

从按下开始到第一圈完成的时间混合了起动延迟和加速过程，不能直接称为稳定转速。优先在连续旋转中用相邻同相位地标回归事件计时，并检查逐圈速度是否稳定。起动过程单独记录；如果持续时间或输入历史显著改变速度，静态反曲线只说明稳定状态，不能承诺已经消除加速、平滑或延迟。引擎本身可以串联死区、响应曲线、逐帧平滑等输入处理，这也是需要区分这些因素的依据。[Epic 输入处理说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/enhanced-input-in-unreal-engine)

视觉识别要结合多个背景特征、几何一致性与沿途地标顺序；先确认已经离开起始朝向，再允许记录回归事件。刚开始时画面相似、重复纹理或错过高速回归都不能计为完整一圈。HUD、枪械和移动目标不参与地标匹配。特征匹配与几何校验是候选实现，是否能在具体游戏中可靠计圈仍需实测。[OpenCV 特征匹配与几何校验](https://docs.opencv.org/4.x/d7/dff/tutorial_feature_homography.html)

低力度可能需要很长时间才能转满一圈。未完成周期标为未完成，不记成零响应；可以用局部运动区分“可观测到缓慢运动”和“在噪声范围内未观测到运动”，并输出死区上下界，不能因为等待超时就断言死区。光流保留为起动、稳定性和低速测量的辅助工具，不能替代可靠整圈计时的角度尺度。[OpenCV 光流说明](https://docs.opencv.org/4.x/d4/dee/tutorial_optical_flow.html)

垂直视角通常有俯仰限位，不能套用完整 360° 测量，也不能从水平结果推断垂直曲线。未实现可靠的垂直角度测量时，结果明确限定为水平响应校准。

腰射和开镜分别测量，水平正负与垂直正负分别记录；实际实现还需要斜向检查，区分径向、轴向和方向耦合，不能仅测向右就宣称整个摇杆已线性化。未测方向不套用猜测结果。采样必须关联最终已送出的摇杆命令和画面源时间，估计响应延迟并分离起动瞬态与稳定响应；沿输入档位回扫，以识别加速度或时间依赖。时间依赖明显、模型无法解释或画面纹理不足时，不生成可启用的静态补偿。

游戏的起动死区、手柄中心漂移和物理分辨率是不同问题。补偿不承诺数学上的绝对零死区：手柄报告量化、游戏非零最小速度、噪声和采样误差限制了可观测的最小响应；精校结果应展示起动区间、可测的最小输入与复测误差。中心恰好为零时不产生运动，物理手柄持续非零的漂移不会因此消失。[Microsoft XInput 与死区](https://learn.microsoft.com/en-us/windows/win32/xinput/getting-started-with-xinput)

校准文件采用独立的 `game_stick_calibration` 格式，包含版本、游戏、模式与方向、零输出约定、原始样本、拟合、复测结果和当时的灵敏度/FOV/游戏曲线设置。修改这些游戏设置后，需要重新确认或校准。Profile 持有校准快照，曲线预设不能隐式启用补偿。

当前原生 [game_stick_transfer.h](../../native/controller_native/game_stick_transfer.h) 只支持一组死区、幂指数与轴向/径向方式，[output_composer.cpp](../../native/controller_native/output_composer.cpp) 在最终输出边界使用它；还不支持任意校准 LUT、方向差异或腰射/开镜分组。后续落地要扩展这个所有权层，同时让控制器的已交付命令解码使用相同映射，避免重复反算和错误学习。当前响应学习不能替代这次独立校准。

视觉稿提供可操作的分步流程、模式与方向选择、失败重采、对比图、写入草稿和导出。它使用明确标记的理想模拟模型 `d=0.16, e=2.2`，没有采集游戏画面，也没有发送摇杆输入。流程说明现已改为整圈定标与局部加密，结果区改为整圈周期、复测偏差待实测，并限制为左右水平转向；后台模拟曲线仍来自该理想模型，不是实测结果。

### 内存帧率：查看本次 Aim 的处理速度

运行反馈现在展示应用平均 FPS、Aim 平均 FPS、近 5 秒 Aim FPS，以及 Aim 累计时长、帧数和当前状态。启动原生程序即开始统计，不需要打开日志或点击录制。没有 Aim 时间时显示 `—`；处于 Aim 但没有新帧时显示 `0.0`，避免用上次正常工作的数值掩盖停顿。

Aim 定义为实体开镜状态，沿用原生的 `physical_ads_active`；丢目标、没有新视觉帧但仍开镜的时间也属于分母。整体平均值则包含开镜和空闲的全部运行时间。帧按控制器实际消费时的开镜状态归类，相邻采样之间的时长属于前一个状态。BodyLock、腰射辅助和游戏渲染 FPS 若需要展示，应成为另外明确命名的指标，不混入这项平均值。

本次平均值为 `Σ Aim 有效帧数 ÷ Σ Aim 有效时长`，不能对各窗口的 FPS 简单平均。例如两段分别为 180 帧/1 秒、640 帧/4 秒，平均值为 164 fps；两段之间的空闲时间不计入。仍处于 Aim 但应用停顿的时间要计入，不能只累加收到帧的瞬间。有效帧指新提交并实际消费的视觉结果，重复消费、轮询次数和 DXGI accumulated frames 不增加这个分子。它是应用视觉帧率，不是游戏的呈现帧率、控制循环 Hz 或推理耗时的倒数。

为避免查看帧率反而增加日志开销，统计采用纯内存通道。原生 [frame_rate_counter.h](../../native/runtime_app/frame_rate_counter.h) 使用累计整数计数和 51 个固定时间桶，计数器小于 4 KiB；控制线程沿用已有时间戳，在输出完成后更新计数，不分配内存、不加锁、不调用系统接口，也不格式化或写文件。最近窗口取最新完成的 100 ms 边界之前的最多 5 秒，精确累加该窗口的 Aim 时长与帧数；不足 5 秒时用已经累计的时长。任意长的停顿仍计入累计分母，更新最近窗口时最多触及 51 个桶。

现有后台控制桥接线程约每 500 ms 发布固定大小的共享内存快照。控制线程约每 500 ms 尝试交付一次快照，锁忙时直接跳过本次交付；累计计数继续更新，下一次快照仍包含这些帧。GUI 在原有后台观察器里读取，界面只更新变化的文本。原有配置重载与响应学习协议保持不变，新增帧率通道为独立的 112 字节内存映射，不写 JSONL 或统计日志。此前设计中的持久化记录与趋势演示没有接入桌面版本。

每次启动清零，数据绑定运行 PID、进程创建时间和实际运行 Profile，切换编辑对象不会改变它。停止时原生发布最终内存快照；进程退出后通道释放，GUI 只保留最近收到的数据，因此停止后展示不保证是最终精确总数。关闭 GUI 后不保留历史。配置库、启动状态及旧日志功能仍沿用各自的机制，这项统计不读取日志，也不会自动打开任何日志开关。

验证覆盖时长加权平均、零时间空态、无帧等待、24 小时停顿、两组独立种子的 786,432 次随机更新、共享内存发布与资源释放。Python 测试通过真实只读内存映射读取，并禁止文件读写接口，检查会话身份、协议和计数校验；真实 Tk 测试检查数据展示、配置切换、缓存页面与新会话清零。测试不测量游戏呈现帧率或证明实机 CPU 收益。捕获到输出延迟、P95 和 1% low 尚未增加，不能由这些计数推导。

此次补充的 23 项浏览器检查覆盖点位精校与错误输入、校准失败/复测/保存/配置隔离、中立与微输入反函数、按 Aim 时长计算平均、空闲窗口、停止记录与性能记录隔离，并检查 840×680 下的关键操作与横向溢出。测试脚本为 `runs/desktop-ui-design-20261004/verify_additions_1.cjs` 至 `verify_additions_3.cjs`；这仍是视觉稿验证，不能证明实际游戏测量精度或原生性能采集已完成。

## 配置与状态的设计边界

桌面版本已经采用独立 Profile 文档：游戏在创建时确定，原生配置从文档生成。已有配置通过显式导入解析为新快照；界面不自动显示历史场景作为模板，也不在打开时猜测用户要哪种曲线。配置存储界面参数与导入文件显式指定的其他参数，其余未指定项继续采用原生默认值。

每份 Profile 保留自己的初始快照，恢复创建时的值不读取正在变化的全局配置。原生运行配置投影为 TOML，加载器接受显式声明游戏的独立文件并拒绝跨游戏使用。控制算法与输出链不改动。切换编辑对象、保存配置和切换运行配置由不同动作驱动。

空配置库显示新建入口和必要的名称、游戏选择，不堆放不可编辑的历史配置。模型缺失时在设备与运行中说明缺少哪个文件；参数非法时在对应行说明允许范围；程序忙碌时禁用会冲突的操作；启动失败时保留草稿与错误信息。运行反馈没有数据时使用空态，不以演示数值冒充原生观测。

用户调整瞄准时，先要知道当前参数影响哪一步。开镜后的首次瞄准负责把准星拉向目标，之后的持续跟随负责随目标移动并纠正偏差。原界面将两类参数都称为水平、垂直辅助，又把倍率与上限分在不同页面，读者容易将它们理解成重复的力度设置。当前两阶段统一显示 0～100% 的横纵输出上限，响应时间单独以毫秒输入。参数页的 ADS 快捷编辑和范围页共享同一份变量；阶段切换不改变数据，配置读取边界负责旧参数换算。

范围调校按“选择阶段 → 调整参数 → 查看目标位置和辅助结果”组织。顶部以分段按钮选择 ADS Snap 抓取或 BodyLock 跟随，右侧只显示对应参数，L2 阈值保持可见。删除按焦点与参数编辑自动切换阶段的路径，避免用户同时面对两种模式所有者。默认只显示当前阶段的范围圈；需要比较时勾选“对比两圈”。居中、圈内、圈外提供可重复的示例位置，仍可直接点击和拖动。

画布集中展示准星、目标和范围，纠偏方向与估算力度放在右侧参数下方，不挤占图示高度。ADS 接入直接输出上限与原样生效的响应时间；BodyLock 接入独立的横纵响应时间和上限。两阶段共同使用 AI 输入死区，示例显示被过滤的轴。新拾取和已选目标的跟随分别检查自己的范围与外形条件。无效的另一阶段草稿仅隐藏对应比较圈，不替换成默认值。静止目标、线性响应、完整权限的示例用于解释参数关系，真实工具曲线、学习、识别和手动权限仍决定游戏中的输出。

尺寸用外形选择、百分比输入及小中大示例调整，拖动只移动示例目标。范围图例明确圆圈、准星和瞄点的含义，L2 的实际阈值继续在右侧调整。纠偏图按固定目标、曲线与限幅前的需求说明参数作用，避免把内部像素参数误认为另一种目标范围，或把示意当成游戏实测轨迹。

参数调校的高级入口位于两列常用参数下方，左对齐并单独占一整行，以箭头表示展开和收起。高级内容在其下方复用两列布局。它控制界面内容的可见性，避免用运行开关的外观暗示算法启停。短页的滚动区域至少覆盖视口，从滚动组件修正向上滚动产生顶部空白的问题；展开、收起和缩放仍能正常更新范围。

表单的对齐和留白遵循共同布局规则。Apple 的[布局指南](https://developer.apple.com/design/human-interface-guidelines/layout)强调控件对齐、分组和周围留白；[Fluent 2 布局规范](https://fluent2.microsoft.design/layout)使用以 4 px 为基础的间距体系，并区分组件内间距、分组间距与页面边距。这里采用这些原则，具体尺寸按本应用的桌面密度选择，不照搬触屏表单的高度。

默认比例下，页面左右各留 24 px，双列间隔 24 px，参数标签列 144 px，标签与控件间隔 12 px。所有数字输入框共用 88 px 的数值栏，以及 4 px 间隔加 24 px 的单位槽；没有单位时仍保留槽位，所以 ×、% 不改变滑条长度或输入框位置。滑条占用数值栏之前的剩余空间。模型路径和菜单按文本内容使用较宽控件。参数行上下各留 2 px，相邻输入框之间有 4 px 空隙，分组之间留 8 px；紧凑范围页通过标题和留白区分阶段，省去重复分隔线。尺寸统一在共享组件中持有，避免后续参数各自决定宽度。

范围示意的高度由页面视口分配，说明文字先占位，画布使用剩余空间。原先从预览自身的请求高度反推画布高度，会在文本换行时令滚动条反复出现和消失；新的布局取消了这一反馈路径。几何回归检查带单位与无单位的滑条长度、数值栏边缘、参数行空隙，以及窗口缩放后的布局收敛和说明文字完整性。840×680、900×740、1120×840 的首屏与截图均在独立 Windows 桌面验证。
