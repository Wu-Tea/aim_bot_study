# 独立 cue 检测的识别帧率开销

用户观察识别帧率由160–170降到90–110，询问是否cue/person同步等待；随后说明同步前未留意，不能确定下降发生在哪次更新。本轮只诊断，没有修改生产代码、个人配置或clean。

## 已确认的执行路径

`vision_engine.cpp` 当前依次执行：GPU person推理及结果等待 → 颜色画面回读并等待 → CPU selector（颜色注解、独立cue检测、关联、纹理跟踪）→ 发布结果。

不是两个独立检测线程互相等待。cue检测在person推理结束之后串行运行，两者完成后才发布同帧结果。`required_color_region()`在启用cue identity时无条件要求完整640×512截取框；`CueDetector::detect()`逐像素进行颜色分类，再遍历同色连通区域和形状筛选。它不是第二次神经网络推理。

## 同输入实测

输入：用户10月22日两个拼接片段，665帧。原生Release工具、同一480×384 TensorRT模型、生产0.40解码门槛、640×512截图；调用生产函数限制在6个E核，与10月23日运行日志一致。对每帧先取得原始person检测结果，然后对相同原始像素/检测结果分别运行独立cue模式和旧selector模式。每个CPU模式3轮、交替执行顺序，丢弃各轮前30帧，得到每模式1905个计时样本（635独立视频帧），不计文件解码和磁盘读取时间。

| 阶段 | 当前版本平均 | 当前P95 | 同步前71f9104平均 |
|---|---:|---:|---:|
| 开启独立cue的CPU selector | 4.167 ms | 5.553 ms | 4.033 ms |
| 关闭独立cue的旧CPU selector | 0.130 ms | 0.439 ms | 0.131 ms |
| 单独完整cue检测 | 4.082 ms | 5.391 ms | 3.919 ms |
| 完整截图GPU→CPU回读并等待 | 0.068 ms | 0.069 ms | 0.069 ms |
| person推理调用墙钟时间 | 0.824 ms | 0.940 ms | 0.852 ms |

单独cue是另行调用计时，用于定位selector的主要成本，不能把它再加到selector总时间里。推理/回读每帧只实测一次，跨模式/轮次复用值。同步前对照使用Git提取的71f9104 selector/cue实现及匹配头文件，其余无变更生产依赖使用当前库。关闭cue仅是分析对照，不是产品建议：它会改变目标覆盖及身份行为。

当前独立cue相对关闭cue的selector增加约4.037ms。若原链路160–170fps对应每帧5.88–6.25ms，串行增加此成本后约97–101fps，与用户90–110量级相符。这个换算是解释性估计，不是游戏负载下完整管线帧率实测。

同步前已有约4.03ms的开销；本次运动参考/弱框修复不是本实验中约4ms增量的起点。当前/前版0.13ms的小差异不足以在非隔离系统里归因到某条新增语句。回读同步的实测成本远小于CPU cue检测；不能仅去掉`cudaStreamSynchronize`，否则CPU可能读到未完成的数据。

## 结论与优化方向

主要可复现开销是独立cue每帧全框CPU颜色及连通区域扫描，并串行放在person推理之后。优先优化这段计算（例如GPU颜色筛选或保持检测语义的CPU批量计算），再评估同一帧的cue/person并行，关联在两者完成后进行。并行不能直接消除全部cue计算时间；使用陈旧cue、降低cue频率或强制裁剪到人体框会改变已接受的独立索敌和漏检续跟行为，不应作为默认提速方式。

本轮没有游戏GPU竞争、DXGI捕获/映射、实时控制线程和GUI的完整负载；实际推理及等待会随游戏变化。最新运行日志关闭perf_summary，普通控制遥测也没有各阶段完整计时，无法据现有日志确定降帧开始的准确版本或把全部实机变化归因于此。已定位可解释大部分量级的算法成本，不宣称排除所有环境因素。
