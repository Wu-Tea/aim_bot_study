# 手柄助手 GUI

双击仓库根目录的 `启动助手.vbs`，在同一个窗口选择游戏、保存设置、启动和停止应用。
GUI 使用本机已有的 `D:/env/python/pythonw.exe`，界面使用 Python 标准库 Tk，不需要安装浏览器前端或新的推理环境。
游戏运行时仍是 `native/vision_native/build/Release/cod_native_runtime.exe`，保持原有 HidHide 放行路径。

## 使用

1. 先接好并打开实体手柄，选择通用 / COD、Apex Legends 或 COD：Black Ops III。
2. 在“当前游戏设置”调整模型、友方判断、目标点、响应曲线、ADS 力度、压枪、fire 按键和死区补偿。帧率、输入选择和日志在“共用设置”。
3. 点击启动。有未保存的修改时，按钮会先保存再启动；切换正在运行的游戏时，会先正常停止旧实例再启动新实例。
4. 停止运行使用窗口上方的停止按钮。关闭窗口会保留运行程序，重新打开可接管当前会话。

GUI 是单独的 Python 进程，主程序是原来的 C++ runtime。可以在主程序停止时打开 GUI 编辑配置，也可以关闭 GUI 继续使用主程序，之后重新打开接管。
打开 GUI 不启动主程序，停止主程序不关闭 GUI；主程序的控制循环和推理不依赖界面存活。

界面会区分正在启动、等待手柄、运行中、正在停止、已停止与启动失败。
“启动识别”显示初始化时发现的手柄及虚拟输出结果，**不代表持续实时监测设备连接**。
初始化时未发现手柄会显示等待手柄；请连接手柄后停止并重启，尤其是使用 SDL 的 DualSense。
失败时界面展示日志错误，详细启动输出可通过“查看日志”读取。

通过 GUI 或统一后台入口启动的实例有统一进程记录，GUI 核对可执行文件路径、PID 和创建时间后接管，不需要重新启动 runtime。
旧前台 `gamepad_start.bat` / `gamepad_native_cpp_start.bat` 和直接运行 exe 不写该记录，当前 GUI 无法完整接管，可能显示已停止；启动保护仍会扫描同路径进程并阻止重复创建。
这项限制与“启动识别并非实时手柄连接状态”是两个不同的待补齐项。

运行时修改参数后点击“保存并应用”：支持的参数直接热重载，不支持的参数会提示需要重启。
“热重载”按钮重读已保存的配置；即使文件未变化，成功重载也会清理响应学习。
“重新载入”只把文件读回 GUI，不改变运行参数。
“高级配置”提供完整 TOML 编辑器，覆盖未列入普通表单的设置。

## Fusion 开关

Fusion 有单独的状态行与“开启 Fusion / 关闭 Fusion”按钮，按钮根据实际画布进程切换。
启动主程序不会自动打开 Fusion；关闭 Fusion 不停止主程序；停止或重启主程序不关闭 Fusion。主程序停止时，画布保留并等待数据。
关闭 GUI 保留主程序与画布，重新打开可接管两者。旧版保存的“随主程序启动 Fusion”偏好不再使用。
首次开启 Fusion 需要主程序已初始化，以提供检测数据；未准备好时按钮禁用。已经开启的 Fusion 随时可以单独关闭。
开关控制显示进程，原生 Fusion IPC 通道保持待命，以支持运行中重新打开。

GUI 使用原有 Fusion 启动脚本的 `-AttachOnly` 模式，并核对画布连接和运行状态。即使主程序在启动期间退出，该模式也不会擅自启动另一个主程序。
原有独立 Fusion 脚本不带该参数时仍保留其历史自动启动行为。启动器输出写入文件，避免 Windows 子进程继承输出管道导致 GUI 等待画布整个生命周期。

## 热重载范围

| 参数 | 运行中应用 |
| --- | --- |
| ADS 水平、垂直力度；持续跟随水平、垂直力度 | 支持 |
| 固定压枪开关、下压力度、腰射倍率 | 支持 |
| 自动开火输出 RT / RB；手动开火输入 both / RT / RB；手动开火激活 AI | 支持 |
| 友方判断、目标点高度、宽低目标点高度 | GPU Vision Service 路径支持 |
| 模型、捕获/输入尺寸、帧率、性能档位、曲线、死区补偿、手柄选择、日志等其余设置 | 需要重启 |

`manual_fire_input = "both"` 保持原有 RT 或 RB 均视为手动开火的行为。改成 RT 或 RB 后，AI 激活、手动开火接管和压枪使用同一个绑定判断。
`fire_output` 则指定自动开火输出。两者都可动态切换，实体按键仍按原样透传。
切换时取消旧配置的自动开火脉冲，重新满足有效目标和开火条件后才能产生新脉冲。

重载在后台读取并校验文件，在控制 tick 的边界应用。友方/目标点修改还需等待带有新策略版本的新视觉帧；旧帧不会被标成新配置帧。
界面区分“已受理、等待帧”和“已经生效”。同时改动支持和不支持的参数时，整次重载都提示重启，避免部分参数生效。
上一次重载尚未完成时，新请求会明确提示未提交；完成后需要再次点击热重载，不会用旧请求的确认冒充新配置已经生效。
同步旧 Vision 路径下的友方/目标点修改也会提示重启。

成功应用后清理 ADS 与持续跟随响应估计器、普通/减速区的学习系数、置信度、有效样本、激励历史和命令/帧配对历史，防止旧配置样本进入新学习。
目标身份、ADS 生命周期和手动输入状态继续由原有逻辑管理。被拒绝或需要重启的请求不会清理学习。

## 学习参数

“学习参数”页约每半秒更新四个区域：持续跟随普通区、持续跟随减速区、ADS 普通区、ADS 减速区。
每区显示生效系数、学习系数、置信度与有效样本数，没有有效样本时明确显示“未学习”。
系数单位为像素 /（有效摇杆 × 秒）；它是控制器根据目标误差和已输出命令推断的响应，不能当作独立测得的游戏灵敏度。
生效系数结合了配置初值与置信度，可能不同于原始学习系数。

“导出学习数据”把当前数值、配置版本、fire 绑定、区域顺序、单位、采样时间、导出时间和运行实例写入 `runs/desktop/learning/<时间>.json`。
当前提供查看与导出，尚无手动编辑或导入学习系数的入口。未来需要在估计器层定义覆盖值与自动学习的关系，避免直接写一个下一帧就被重新估计的数值。

## 一份配置的归属

`config.toml` 的原有分块作为共用值，游戏分块只写差异。例如：

```toml
[games.apex.runtime.vision]
model_path = "artifacts/game-specialists-20260914/exports/apex/apex_480x384.engine"

[games.apex.gamepad.aim_response_curve]
algorithm = "linear"

[games.apex.gamepad.recoil]
hipfire_multiplier = 0.5

[games.bo3.gamepad.output_transfer]
enabled = true
deadzone = 0.20
axial = false
game_exponent = 1.0

[games.bo3.gamepad.aim_response_curve]
algorithm = "linear"
```

通用 / COD 页面编辑共用值，其他游戏页面编辑各自的差异；共用设置页始终编辑共用值。
“继承共用”表示该字段未写入游戏分块，修改后会成为游戏专属值。
若要恢复继承，在高级配置中删除该游戏分块对应的键。
BO3 的本机死区补偿已从旧文件迁移为 0.20；示例文件的 0.16 只是初始假设，均不是游戏实测结论。

原生程序直接读取分块：`--config config.toml --game apex`，不生成另一份启动配置。
配置加载先用游戏值替换对应共用键，再调用各项设置函数一次，避免力度派生计算重复相乘。
省略 `--game` 时读取 `[runtime].game`，没有该键则为 `default`；GUI 始终明确传入所选游戏。
现有环境变量覆盖仍由原生程序处理，可能优先于文件值；普通表单展示的是文件配置。

GUI 保存时先校验 TOML 和原生各游戏的配置，成功后备份原文件到 `runs/desktop/config-backups/`，再原子替换。
检测到外部修改会拒绝覆盖并要求重新载入。仅查看界面与启动应用不会改写配置。
旧 `config.bo3.toml` 和转换助手不再参与普通启动，保留以便核对历史设置；之后只编辑统一配置。

## 启停与日志

GUI 和旧后台 PowerShell 入口使用同一个 `desktop_app.runtime.RuntimeManager`。
进程记录统一为 `runs/runtime/background/native_runtime_state.json`，包含路径、PID、创建时间、游戏和日志位置。
启动锁防止多个入口同时创建第二个实例；停止前核对进程路径和创建时间，避免 PID 被复用时停止其他程序。

停止通过按 PID 命名的 Windows 事件请求 `RuntimeLoop::request_stop()`。
原生监听线程阻塞等待事件；控制循环正常结束后执行已有的输出中和、视觉与工作线程退出流程。
GUI 不在控制 tick 内运行界面逻辑或读配置文件；原生 tick 检查准备好的配置并约每半秒提供固定大小的学习快照。停止超时会报错，不自动强杀或并行启动另一实例。
旧版本进程若没有退出事件，须先通过其原入口停止，再使用更新后的运行程序。

每次启动的标准输出与错误日志写入 `runs/desktop/sessions/<时间-编号>/`。
结构化控制/性能日志仍遵从原配置。会话 manifest 描述启动配置；热重载的生效版本与参数另记在标准输出的 `[RuntimeControl] applied revision=... learning_cleared=1` 中。
分析跨重载的会话时，应结合这些版本记录，不能把启动 manifest 当作全程配置。
原有 Fusion 显示入口仍可连接统一记录中的运行实例。
